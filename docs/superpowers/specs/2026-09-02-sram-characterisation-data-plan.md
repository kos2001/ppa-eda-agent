# Filling the SRAM data gap

`sram_wrapper` has never closed, and two different shortages get called
"missing data". They are not the same shortage and only one of them can
be worked on first.

| | what is missing | can it be filled now |
|---|---|---|
| **A. model samples** | 3 macro configurations recorded, 0 passing | no — see below |
| **B. characterisation** | no measured timing above 0.04 ns input slew | yes |

**B is the prerequisite for A.** Every `sram_wrapper` run dies at
`RSZ-0090` before producing a distinguishing outcome, so running more
configurations today adds failures that all fail identically. The labels
A needs do not exist until B removes the wall.

## What B actually requires

`pipeline/recharacterise.py` establishes that the 0.04 ns is
`slew_scales [0.25, 1, 8]` × sky130 `rise_time` 0.005 ns — where the
macro's characterisation stopped, not a limit the SRAM imposes. Filling
it means generating the macro again over a slew grid that covers the
0.209 ns this design really reaches.

Read out of the generator rather than assumed:

- The macro is regenerated by
  [VLSIDA/sky130_sram_macros](https://github.com/VLSIDA/sky130_sram_macros)
  from `configs/sky130_sram_1kbyte_1rw1r_32x256_8.py`, which sets only
  shape (`word_size` 32, `num_words` 256, `write_size` 8, 1rw1r) and
  execs `configs/sky130_sram_common.py` for everything else. A `Makefile`
  drives it with `TECH = sky130`.
- `sky130_sram_common.py` sets `nominal_corner_only = True`,
  `route_supplies = "side"`, `check_lvsdrc = True`, `uniquify = True`.
  It carries **`#analytical_delay = False`, commented out.**
- In OpenRAM's `compiler/globals.py`, `analytical_delay` defaults to
  true; `-c/--characterize` sets it false, described as "Perform
  characterization to calculate delays (default is analytical models)".
- `compiler/characterizer/lib.py` computes `slews = slew_scales *
  tech.spice["rise_time"]`, and `slew_scales` is a config option
  (`compiler/options.py`) defaulting to `[0.25, 1, 8]` in `globals.py`.

So the shipped liberty's numbers come from **analytical models on a
three-point grid**, and both facts are config lines.

### The change

```python
# configs/sky130_sram_1kbyte_1rw1r_32x256_8.py — or a local copy
analytical_delay = False          # SPICE, not the analytical model
slew_scales = [0.25, 1, 8, 48]    # 48 * 0.005ns = 0.24ns, covers 0.209ns
```

`recharacterise.py --worst-slew-ns 0.209` computes that `48` and prints
the resulting grid, so the number is derived rather than picked.

### Cost, from the generator's own threshold

OpenRAM warns that characterising is slow only above `2**14` bits. This
macro is 32 × 256 = **8192 bits, half that**, so it sits under the line
the tool itself draws. That bounds the risk; it does not make the run
free, and the wall-clock cost is unknown until someone runs it.

### What must be checked before trusting the result

A regenerated macro is a new GDS, LEF and liberty, not a patched number.

1. `characterisation_ceiling()` on the new lib reports >= 0.24 ns, and
   `max_transition` moves with it — otherwise the config did not take.
2. The new `index_1` still contains the original three points, so
   existing measurements were extended rather than replaced.
3. DRC and LVS pass on the new GDS (`check_lvsdrc = True` already).
4. `sram_wrapper` re-runs and `RSZ-0090` is gone. If it is not, the
   ceiling was not the binding constraint and this plan was wrong —
   which is a result worth having.

## Then, and only then, A

With the wall gone, `sram_wrapper` produces runs that differ, and macro
samples become worth collecting: `collect.py`'s existing axes
(`FP_CORE_UTIL`, `SYNTH_STRATEGY`, `CLOCK_PERIOD`) apply unchanged.

The target is set by measurement, not preference. `surrogate.py` scores
99% of folds on area and 98% on power against **65% on pass/fail**, and
pass/fail is the one a candidate search would need.
`tests/test_learned_model_fit.py` pins that split, so it moves when the
corpus does.

## What this plan does not claim

- That regeneration closes the design. It removes one blocking failure;
  the 0.209 ns slew is still 5.2x what was characterised, and whether
  the macro is actually happy there is exactly the question SPICE would
  answer.
- That more samples fix the pass/fail model. That is a hypothesis the
  scored corpus can test once the samples exist.
- Anything about the other macros in the repo. Each ships its own
  liberty and would need its own check.
