# Reading Synopsys PrimeTime `report_timing`

## Where it comes from

Generated by PrimeTime (PT) via `report_timing`, run in signoff STA on a
post-synthesis or post-layout netlist with SDF/SPEF back-annotation. DC's
own internal timing reports (from `compile_ultra`) use a similar format but
are less trustworthy for signoff — always treat PT as the source of truth
once it's available in the flow.

## Typical structure (single path report)

```
****************************************
Report : timing
        -path_group reg2reg
        -delay_type max
Design : top_module
Version: T-2022.03-SP5
Date   : ...
****************************************

Startpoint: u_fetch/pc_reg[12] (rising edge-triggered flip-flop clocked by CLK)
Endpoint: u_decode/instr_reg[3] (rising edge-triggered flip-flop clocked by CLK)
Path Group: reg2reg
Path Type: max

Point                                  Incr       Path
--------------------------------------------------------
clock CLK (rise edge)                  0.00       0.00
clock network delay (propagated)       0.45       0.45
u_fetch/pc_reg[12]/CK (DFFR_X1)        0.00       0.45 r
u_fetch/pc_reg[12]/Q (DFFR_X1)         0.12       0.57 f
```

## Key concepts

- **Path group** — paths are bucketed (`reg2reg`, `in2reg`, `reg2out`,
  `in2out`, plus per-clock groups). Always check which group a critical
  path belongs to; a violation on `in2reg` often points to a slow input
  driver/IO timing budget, not internal logic.
- **Data path vs. clock path** — the first block (arrival time) is the
  logic path from launch flop to capture flop. The second block (required
  time) is the clock path to the capture flop plus setup/hold margin. The
  clock path itself can dominate — check clock network delay before
  assuming the data path logic is the bottleneck.
- **Slack = data required time − data arrival time**. Positive
  (`MET`) is fine; negative (`VIOLATED`) is a timing violation. **WNS**
  (Worst Negative Slack) is the single worst violation; **TNS** (Total
  Negative Slack) sums all violations — WNS tells you how bad the worst
  path is, TNS tells you how widespread the problem is.
- **Setup vs. hold** (`-delay_type max` vs `-delay_type min`) — setup
  violations mean data arrives too late relative to the clock (fixed by
  speeding up the data path or slowing the clock); hold violations mean
  data arrives too early relative to the same clock edge (fixed by adding
  delay, never by speeding anything up — a hold fix that speeds up a path
  makes hold worse, not better).
- **Clock uncertainty** — models jitter/skew margin; a large uncertainty
  value eating into required time is a clock-tree/PLL quality issue, not a
  logic-path issue.

## Common patterns and what they mean

- **A handful of paths dominate WNS/TNS**: check if they share a common
  startpoint or endpoint (fan-out bottleneck) or a common intermediate cell
  (a single slow buffer/gate feeding many paths) — fixing that one point
  fixes many paths at once, cheaper than fixing each path individually.
- **Violation is entirely in the data path (arrival time too large), clock
  path delays look symmetric**: classic combinational logic problem — deep
  logic depth or high-fanout nets. Candidate fixes: cell upsizing,
  restructuring (e.g. splitting a wide AND-tree), adding a pipeline stage
  (changes microarchitecture, largest area cost but most robust fix).
- **Clock network delay differs a lot between launch and capture points for
  the same clock**: clock skew — often a CTS/floorplan issue rather than
  something DC-level synthesis can fix. Flag for the physical design stage.
- **Many `in2reg` violations, few `reg2reg`**: input timing budget (SDC
  `set_input_delay`) may be too aggressive relative to what's achievable, or
  the block boundary interface logic is doing too much work in one cycle —
  check with the block's SDC constraints before assuming synthesis quality
  is the issue.
- **Hold violations appear only after a setup fix**: expected — spot-check
  that any setup fix (upsizing/buffering to speed up a path) didn't turn a
  previously-safe hold margin negative on the same or a nearby path.

## Relationship to the other PPA legs

- **Timing ↔ Area**: virtually every setup fix (upsizing, buffering, adding
  pipeline stages) costs area — see `report-area.md`.
- **Timing ↔ Power**: upsized/faster cells draw more dynamic power per
  transition; hold fixes (extra buffers) add both area and switching power
  for no functional benefit — worth minimizing hold-buffer count via SDC
  timing-derate/uncertainty tuning rather than brute-force buffer insertion.

## Format variants

PrimeTime's `Point / Incr / Path` columns (above) aren't universal. OpenSTA
(free, PrimeTime-command-compatible) defaults to `Delay / Time /
Description` columns instead — same `Startpoint:`/`Endpoint:`/`Path
Group:`/`slack (MET/VIOLATED)` structure, different header/spacing. See
`see-also.md` for where this was confirmed and how to get real sample
reports from it.
